# 강화학습 학습 안정화 기록

목표: 학습 곡선이 천천히, 꾸준히 오르게 만들기
판단 기준: 성능이 한두 에피소드 사이에 급하게 뛰지 않고 여러 에피소드에 걸쳐 오름, 오르는 동안 크게 떨어지는 구간이 없음

---

## 테스트 0. 배경 트래픽 방식 변경 (2026-11-05)

- 한 것
  - 배경 트래픽을 새 방식(`P.bgMode = 'event'`, `sim/bg_event.py`)으로 바꿨다. 기존 핫스팟 방식은 `P.bgMode = 'hotspot'`으로 그대로 쓸 수 있다.
    - 기본 부하: 모든 링크에 링크 용량의 0.1~0.4배가 항상 흐름
    - 지역 핫스팟: 포아송 과정으로 발생, 중심 위성의 송신 링크(최대 4개)에 0.5~1.5배를 더함, 지속 평균 1초
    - 혼잡 단계: 핫스팟 발생 간격 평균 base 2초, high 1초, severe 0.5초
  - 에피소드 30초 -> 10초, 평가 에피소드 20개 -> 30개(시드 1~30), 학습 에피소드 60개 -> 150개
  - 기본 부하로 배경 패킷이 크게 늘어 실행이 느려져서, `sim/run_isl_sim.py`의 배경 패킷 생성, 큐 진입, 전송을 반복문 대신 배열 연산으로 바꿨다.
- 이유
  - 기존 환경은 에피소드 하나(30초)에 핫스팟 위치가 한 세트뿐이라 학습할 혼잡 상황이 단조로웠다.
  - 선행 연구 참고: DTAR (기본 트래픽 + 무작위 지역 급증, 시나리오를 섞어 학습), Back-Pressure 부하 분산 라우팅 (버스트 평균 1초)
- 결과
  - 시뮬레이터 속도 개선 전후 결과가 완전히 같음을 확인했다 (hotspot, event 두 방식 모두 패킷별 결과, 결정 기록, 노드 기록 일치). 기존 테스트 8개 통과.
  - 실행 시간: A, B 평가(3단계 x 에피소드 3개) 11분 35초 -> 1분 28초
  - A, B 확인 (단계별 에피소드 3개, 대략적인 값)

    | 단계 | A 도착률 | B 도착률 | A 최대 연속 손실 | B 최대 연속 손실 |
    |---|---|---|---|---|
    | base | 97.39% | 98.28% | 26 | 26 |
    | high | 95.67% | 98.33% | 48 | 26 |
    | severe | 86.33% | 91.44% | 85 | 73 |

- 판단
  - 단계가 올라갈수록 손실이 늘고, B가 A보다 낫다. 환경이 단계별로 의도대로 동작한다.
  - severe의 손실률(9~14%)은 중간 정도라, 더 어렵게 하려면 핫스팟 세기나 발생 빈도를 올린다.
- 코드 상태: 유지

### 테스트 0-2. 현실에 가까운 지역 혼잡으로 조정 + 혼잡 단계 한 칸씩 올림 (2026-11-05)

- 한 것
  - 에피소드를 다시 30초로 (평가 20개 = 10분, 시드 1~20, 학습 60개)
  - 기본 부하 유지(0.1~0.4배), 핫스팟 중심을 주 흐름 지역(출발 -> 도착 대각선 1칸 이내)에서 3배 더 자주 뽑음
  - 지역 범위: 중심 위성 송신 링크(0.5~1.5배) + 이웃 위성 송신 링크(그 절반), 지속 평균 2.5초
  - 혼잡 단계: 이전 high를 base, 이전 severe를 high로 옮기고, severe는 최악 상황으로 새로 만듦
    - 발생 간격 평균 base 2.5초, high 1.25초, severe 0.625초 (동시에 걸린 지역 약 1, 2, 4개)
- 이유
  - 교수님 의견과 현실 ISL 트래픽 특성: 기본 부하 위에 수요가 많은 지역 중심으로 혼잡이 생기고, 혼잡은 짧은 버스트보다 길게 이어짐
  - 최악 상황에서 강화학습이 기존 방식보다 연속 손실을 얼마나 줄이는지 확인하기 위해
- 결과 (A, B, 단계별 30초 에피소드 3개, 대략적인 값)

    | 단계 | A 도착률 | B 도착률 | A 최대 연속 손실 | B 최대 연속 손실 |
    |---|---|---|---|---|
    | base (이전 high 값) | 85.43% | 88.33% | 141 | 141 |
    | high (이전 severe 값) | 62.48% | 67.52% | 421 | 277 |
    | severe (새 최악 상황) | 36.26% | 42.15% | 926 | 555 |

- 판단
  - 단계별로 손실이 뚜렷하게 늘고, 최악 상황이 만들어짐
  - 문제: 출발 위성 주변에 핫스팟이 생기면 나가는 링크가 모두 용량을 넘어 어떤 라우팅도 피할 수 없는 손실이 생김 (A, B의 최대 연속 손실이 같게 나오는 이유로 추정). 안전장치를 '용량을 넘는 링크를 빼고도 출발 위성에서 나갈 길이 있는지'로 강화해야 함
- 코드 상태: 유지 (안전장치 보완 필요)

### 테스트 0-3. 안전장치 보완 (2026-11-05)

- 한 것: 핫스팟을 만들 때, 용량을 넘는(1.0배 이상) 링크를 모두 빼고도 출발 -> 도착 길이 있어야 하도록 바꿨다 (`P.evSafeLoad = 1.0`). 못 찾으면 그 핫스팟은 건너뜀.
- 이유: 출발 위성 주변이 모두 넘치면 어떤 라우팅도 피할 수 없는 손실이 생겨 비교와 학습을 흐림
- 결과 (A, B, 단계별 30초 에피소드 3개, 대략적인 값)

    | 단계 | A 도착률 | B 도착률 | A 최대 연속 손실 | B 최대 연속 손실 |
    |---|---|---|---|---|
    | base | 88.81% | 91.20% | 172 | 172 |
    | high | 65.78% | 74.91% | 423 | 334 |
    | severe | 56.65% | 62.96% | 673 | 661 |

- 판단: 피할 길은 남기면서도 severe에서 A, B 모두 40% 가까이 잃는 최악 상황이 유지됨. 핫스팟이 건너뛰어지는 경우는 거의 없음 (30초 평균 핫스팟 수 base 12, high 24, severe 49로 계획과 같음)
- 코드 상태: 유지

## 테스트 1. severe만 20 에피소드 학습 (2026-11-05)

- 한 것: 새 환경에서 학습 단계를 severe만으로 바꿔 C를 20 에피소드 학습했다 (프로젝트 코드는 그대로, 임시 실행 스크립트로 단계만 바꿈). 저장: `~/rl_models/routeC_2026-11-05_3`
- 이유: 최악 상황에서 강화학습이 연속 손실을 얼마나 줄이는지 먼저 확인
- 결과 (학습 중 값, ε 포함)

    | 에피소드 | 1 | 4 | 7 | 10 | 13 | 14 | 15 | 16 | 17 | 18 | 19 | 20 |
    |---|---|---|---|---|---|---|---|---|---|---|---|---|
    | ε | 0.94 | 0.75 | 0.53 | 0.31 | 0.07 | 0.05 | 0.05 | 0.05 | 0.05 | 0.05 | 0.05 | 0.05 |
    | 기한 내 도착률 (%) | 0.44 | 1.72 | 14.61 | 35.00 | 71.56 | 82.67 | 70.72 | 80.44 | 74.94 | 56.06 | 71.61 | 90.44 |
    | 연속 손실 (회) | 9 | 28 | 153 | 130 | 40 | 15 | 10 | 21 | 21 | 47 | 22 | 16 |
    | 최대 연속 손실 (개) | 872 | 297 | 93 | 72 | 40 | 83 | 162 | 41 | 64 | 155 | 86 | 12 |

- 판단
  - 기존 환경과 달리, ε이 최소(0.05)가 된 뒤에도 바로 98%대로 붙지 않고 56~90%에서 오르내림. 학습할 여지가 남아 있는 환경이 됨
  - 에피소드마다 혼잡 배치가 달라 성능 흔들림이 큼. 학습 시드 하나라 우연일 수 있고, 더 많은 에피소드와 무작위 없는 평가로 확인 필요
  - A, B와의 비교는 같은 평가 시드(1~20)에서 ε 0으로 평가해야 함
- 코드 상태: 유지 (프로젝트 코드 변경 없음)

## 준비. 학습 목표 판정 도구와 계획안 설정 적용 (2026-11-05)

- 한 것 (Notion "강화학습 학습 목표 설정" 2~9번에 맞춤)
  - 설정값: 에피소드 10초(`P.simTime = 10000`), 학습 270 에피소드, 학습률 0.0001, 학습 시작 5만, 타깃 갱신 2,500 학습(= 결정 1만 번)마다, 버퍼 100만, ε 감소 결정 30만 번(그대로)
  - `rl/train_rl.py`: 학습 시작 전과 10 에피소드마다 검증 시드 501~505로 ε 0 평가 -> `eval_log.csv` (누적 결정 수, 단계별 도착률, 1분당 연속 손실, 연속 손실 길이 95번째 백분위 등). 학습 시드를 실행 인자로 받음 (`python rl/train_rl.py 270 0 시드`), 저장 폴더 끝에 `_s시드`
  - `analysis/burst_summary.py`: `burst_rate_stats` (1분당 연속 손실 횟수, 연속 손실 길이 95번째 백분위)
  - `eval_routes.py`: C 모델 여러 개(학습 시드별)를 쉼표로 한 번에 평가, 평가 시드별 결과 `per_seed.csv`, summary에 새 지표 추가
  - `analysis/learning_targets.py` (새 파일): 학습 진행, T50, T90, 평가 점 수, 급상승, 수렴, 수렴 뒤 하락, 발산, 학습 시드 간 차이 판정 -> `learning_targets.md`, `learning_curve_eval.png`
  - `analysis/compare_runs.py` (새 파일): B 대비 1분당 연속 손실 감소, 95번째 백분위 감소, 도착률, 지연, 짝지은 승률, 95% 신뢰구간, 최악 에피소드, 이상 신호 판정 -> `targets_report.md`, `.csv`
  - `run.py`: 학습 기본값 270 에피소드, 학습 시드 질문 추가
- 확인
  - 기존 테스트 8개 통과
  - 짧은 설정(에피소드 3개, 2초)으로 학습 -> 검증 기록 -> 학습 곡선 판정 -> 평가(C 모델 2개) -> 최종 성능 판정까지 끝까지 동작 확인
  - 학습된 모델로 검증 함수가 정상 값을 내는지 확인 (base 95.56%, severe 55.00%)
- 코드 상태: 유지 (아직 실제 270 에피소드 학습은 돌리지 않음)
